# 03 功能詳細設計

本文件說明四個功能的設計：picture_quality（即時防呆）、compare（新車損偵測）、tidy（整潔度分類），以及預警與營運流程；最後列出創新服務設計。

---

## 1. picture_quality：照片品質即時防呆（環節一）

### 1.1 目標

使用者每拍一張照片，1 秒內知道要不要重拍，以及具體該怎麼調整。

### 1.2 檢查項目

| 檢查項目 | POC 做法 | 正式版做法（自訓） |
|---|---|---|
| 模糊 | Laplacian variance 低於閾值即判為模糊 | 納入多標籤品質模型 |
| 過暗、過曝、反光 | 亮度直方圖、過曝像素比例 | 同上 |
| 拍攝位置或角度錯誤 | 小型 VLM 判斷這張照片屬於哪一個必拍角度，並和應拍角度比對 | 角度分類模型（MobileNetV3 或 EfficientNet-Lite） |
| 太遠、太近 | 以預訓練 YOLO 偵測車輛，計算車輛框佔畫面比例 | 同左，閾值依角度分別設定 |
| 未拍到車牌、車牌不符 | 車牌偵測加 OCR，和訂單車牌比對 | 自訓台灣車牌偵測器加 OCR |
| 鏡頭髒污、遮擋、手指入鏡 | 小型 VLM | 納入多標籤品質模型 |

### 1.3 執行順序

1. 規則式檢查（模糊、曝光）：未通過就立即回饋，不再往下執行。
2. 車輛偵測：確認畫面中有車，並計算距離是否合適。
3. 車牌與角度判斷。
4. 彙整所有問題，回傳一個最主要的重拍提示，其餘列為次要。

### 1.4 API 規格（草案）

`POST /check-quality`

輸入：照片、訂單 ID、應拍角度（例如 `front_left`）

輸出範例：

```json
{
  "pass": false,
  "issues": [
    {"code": "blurry", "message": "照片模糊，請保持手機穩定後再拍一次"},
    {"code": "plate_missing", "message": "沒有拍到車牌，請把車牌放進畫面中"}
  ],
  "detected_angle": "front_left",
  "latency_ms": 640
}
```

### 1.5 使用者體驗設計

- 回饋要具體，說明「哪裡不對、怎麼改」，不要只顯示「照片不合格」。
- 拍照畫面疊一層車輛輪廓引導框，從源頭減少角度錯誤。引導框也讓不同使用者拍出的角度一致，有助於後續的車損比對。
- 顯示拍攝進度，例如「已完成 5 / 8 張」，並標示還沒拍的角度。
- 連續多次失敗時提供「仍要上傳」選項並標記為人工檢查，避免使用者卡住無法還車。

## 2. compare：新車損偵測（環節二之 1）

### 2.1 目標

比對同一筆訂單的取車照與還車照，找出本次租車新產生的車損。

### 2.2 流程

1. 角度配對：依拍攝角度，把還車照和取車照一對一配對（可沿用 picture_quality 的角度判斷結果）。
2. 影像對齊：以特徵點匹配（LightGlue 或 LoFTR）配合 homography 對齊兩張照片，降低角度差造成的誤判。
3. 候選區域（選用）：對齊後產生差異圖，或以車損偵測模型找出可疑區域，提示大型模型重點查看。
4. 大型模型判讀：兩張照片一起送入大型 VLM，要求輸出結構化 JSON。
5. 排除既有車損：和該車既有車損紀錄比對，已知車損不重複預警。
6. 依信心分數分流（見第 4 節）。

### 2.3 輸出格式（草案）

```json
{
  "new_damage": true,
  "items": [
    {
      "location": "左前保險桿",
      "type": "刮傷",
      "severity": "輕微",
      "bbox": [412, 530, 618, 602],
      "confidence": 0.82
    }
  ],
  "reason": "還車照左前保險桿下緣出現約 10 公分的白色刮痕，取車照同位置無此痕跡。"
}
```

### 2.4 Prompt 設計重點

- 明確說明第一張是取車照、第二張是還車照，只回報「還車照有、取車照沒有」的損傷。
- 要求忽略光線、反光、水漬、灰塵、陰影造成的差異。
- 車損類型限定在固定清單內（刮傷、凹陷、破裂、掉漆、燈具破損、其他），方便統計。
- 要求附上判斷理由，供人工確認時參考。

## 3. tidy：車內整潔度分類（環節二之 2）

### 3.1 目標

把車內照片分成三類：髒汙（須立即清潔）、普通、乾淨；髒汙時觸發預警。

### 3.2 評分準則

| 類別 | 判斷準則（草案，拿到主辦方照片後再校正） |
|---|---|
| 髒汙 | 有明顯垃圾、食物殘渣、飲料翻倒、大量泥沙、污漬、菸蒂，或任何會讓下一位用戶不適的狀況 |
| 普通 | 少量灰塵、腳踏墊有少許沙土、輕微雜亂，不影響使用 |
| 乾淨 | 無可見雜物與污漬 |

### 3.3 做法

- 大型 VLM 搭配上述評分準則，並在 prompt 中附上每一類的範例照片（few-shot）。
- 輸出分類、信心分數、判斷理由，以及偵測到的物品清單。
- 同一車的多張車內照片（前座、後座、後車廂）取最差的結果作為整車等級。

### 3.4 延伸：遺留物偵測

在同一次判讀中，要求模型列出看起來屬於乘客的個人物品（手機、錢包、鑰匙、雨傘、包包），偵測到時通知客服聯繫上一位用戶。

## 4. 預警與營運流程（環節二之 3、環節三）

### 4.1 事件分級

| 事件 | 嚴重度 | 系統動作 |
|---|---|---|
| 疑似新車損（高信心） | 高 | 即時通知營運與客服；暫停該車下一筆預約，等人工確認 |
| 疑似新車損（中信心） | 中 | 進入人工審核佇列 |
| 車內髒汙 | 高 | 自動建立清潔工單，通知負責該區域的整備人員；暫停下一筆預約直到清潔完成 |
| 遺留物 | 中 | 通知客服聯繫上一位用戶 |
| 照片品質不足（使用者選擇強制上傳） | 中 | 進入人工審核佇列 |
| 車內普通 | 低 | 列入例行整備排程 |
| 分析逾時或失敗 | 中 | 進入人工審核佇列 |

信心分數的高低閾值在 POC 評估後依實際資料決定（見文件 05）。

### 4.2 通知內容

通知訊息需包含：車號、訂單編號、事件類型、AI 判斷理由、照片縮圖、後台處理連結。

### 4.3 營運後台

| 頁面 | 功能 |
|---|---|
| 車況總覽 | 所有車輛的目前狀態（正常、待清潔、待確認車損、維修中），可依區域篩選 |
| 預警列表 | 依嚴重度與時間排序的待處理事件 |
| 事件詳情 | 取車照與還車照並排、標出車損位置、AI 判斷理由；「確認」與「駁回」按鈕 |
| 工單 | 清潔與維修工單的指派與完成回報 |

人工確認或駁回的結果全部保存，作為日後調整閾值與自訓模型的標註資料。

## 5. 創新服務設計

在基本功能之外，提出以下服務流程優化：

| 構想 | 說明 | 價值 |
|---|---|---|
| 取車前車況透明 | 取車時顯示這台車最近一次的整潔評分與清潔時間 | 降低「承接髒車」的落差感；使用者可選擇換車 |
| 車況責任時間軸 | 每一筆訂單的取還車照片與 AI 判斷串成時間軸 | 車損爭議時快速釐清責任，減少客服處理時間 |
| 拍攝引導 | 輪廓引導框與逐張即時回饋 | 提高照片品質，減少重拍與事後補件 |
| 遺留物主動通知 | 還車後偵測到個人物品，主動聯繫用戶 | 提升好感度 |
| 用戶獎勵機制 | 照片品質良好、車輛保持整潔的用戶給予點數回饋 | 用正向誘因改善整體車況 |
| 整備路線建議 | 依待清潔車輛的位置，為整備人員排出巡迴順序 | 提升整備效率 |
