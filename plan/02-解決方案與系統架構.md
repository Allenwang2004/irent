# 02 解決方案與系統架構

本文件說明整體解決方案、三層架構、延遲考量，以及 POC 的建議技術組合。

---

## 1. 解決方案總覽

系統分成三層：

| 層級 | 對應功能 | 觸發時機 | 延遲目標 | 模型策略 |
|---|---|---|---|---|
| 即時層 | picture_quality | 使用者每拍一張照片 | 1 秒內回饋 | 規則式影像處理加上輕量模型 |
| 分析層 | compare、tidy | 還車照片全部上傳完成後 | 1 分鐘內產生結果 | 大型視覺語言模型（VLM） |
| 營運層 | 預警、通知、工單、後台看板 | 分析層產生異常事件時 | 即時推送 | 事件驅動與規則分派 |

## 2. 架構圖

```
[使用者 App：拍照]
   |
   |-- (1) 即時層：品質檢查 ---------------> 立即回饋「通過」或「請重拍＋原因」
   |
   v 全部照片通過並上傳
[後端 API] --> [照片儲存] --> [事件佇列]
                                  |
                                  v
                    (2) 分析層（平行處理每一張照片）
                        - compare：取車照 vs 還車照，找新車損
                        - tidy：車內整潔度分類、遺留物偵測
                                  |
                                  v
                    (3) 營運層
                        - 依嚴重度分派：即時通知 / 人工審核佇列 / 例行整備
                        - 通知：Slack 或 LINE
                        - 工單：清潔、維修
                        - 後台看板：車況總覽、照片比對、人工確認或駁回
                                  |
                                  v
                    人工確認結果存回資料庫，成為日後訓練資料
```

## 3. 延遲考量

### 3.1 延遲預算（粗估，POC 階段需實際量測）

| 步驟 | 手機端執行 | 伺服器端執行 | 備註 |
|---|---|---|---|
| 模糊、曝光檢查（OpenCV 規則） | 10 至 30 ms | 10 至 30 ms，另加上傳時間 | 運算很輕，適合放手機端 |
| 輕量分類或偵測模型（MobileNet、YOLO nano 等級） | 20 至 80 ms | 約 50 ms，另加上傳時間 | 手機端需轉成 TFLite 或 Core ML |
| 照片上傳（4G，1 至 3 MB） | 不適用 | 0.5 至 3 秒 | 最大變數；應先在手機端縮圖壓縮 |
| 小型 VLM API（例如 Claude Haiku 4.5） | 不適用 | 約 1 至 3 秒 | 可作為 POC 的即時判斷，但延遲不穩定 |
| 大型 VLM API（例如 Claude Opus 5.5） | 不適用 | 數秒到數十秒 | 只適合非同步分析 |

### 3.2 延遲設計決策

1. 即時層不依賴大型模型。POC 用「規則式檢查，加上小型 VLM」；正式版換成手機端自訓小模型（見文件 04）。
2. 規則式檢查先執行，未通過就直接回饋，不必再呼叫模型，節省時間與成本。
3. 上傳前先在手機端縮圖（例如長邊 1280 px）與壓縮，縮短上傳時間；原圖另外背景上傳，供分析層使用。
4. 分析層非同步執行，使用者按下還車後不需要等待結果。
5. 同一次還車的多張照片平行送出分析，總延遲取決於最慢的一張。
6. 所有 API 呼叫設定逾時；逾時的照片進入人工審核佇列，不影響使用者流程。

## 4. 資料流與資料模型（POC 簡化版）

| 資料表 | 主要欄位 |
|---|---|
| vehicles | 車輛 ID、車牌、車型、既有車損紀錄 |
| rentals | 訂單 ID、車輛 ID、取車時間、還車時間、狀態 |
| photos | 照片 ID、訂單 ID、階段（取車或還車）、拍攝角度、檔案路徑、品質檢查結果 |
| analyses | 分析 ID、照片 ID、類型（compare 或 tidy）、結果 JSON、信心分數、模型名稱、耗時 |
| alerts | 預警 ID、訂單 ID、類型、嚴重度、狀態（待處理、已確認、已駁回）、處理人員 |
| work_orders | 工單 ID、車輛 ID、類型（清潔或維修）、狀態、指派對象 |

## 5. POC 建議技術組合

以下為建議，可依團隊熟悉度調整：

| 部分 | 建議 | 理由 |
|---|---|---|
| 後端 API | Python、FastAPI | 影像與 AI 套件生態完整，開發快 |
| 影像處理 | OpenCV | 模糊、曝光、對齊等基本處理 |
| 物件偵測 | Ultralytics YOLO（預訓練權重） | 車輛與車牌偵測，現成可用 |
| 車牌 OCR | PaddleOCR | 支援中英數，免費 |
| 大型與小型 VLM | Claude API（Opus 5.5 做分析層、Haiku 4.5 做即時層） | 不需訓練即可使用，支援多張圖片輸入與結構化輸出 |
| 資料庫 | SQLite | POC 零設定 |
| 使用者端模擬 | 行動網頁（可呼叫手機相機） | 不需開發原生 App，錄影時也方便展示 |
| 營運後台 | 網頁看板（Streamlit 或 React） | 快速做出可展示的畫面 |
| 通知 | Slack Incoming Webhook 或 LINE Messaging API | LINE Notify 已於 2025 年 3 月停止服務，不可使用 |

## 6. 非功能性考量

- 隱私：照片可能拍到路人臉孔、其他車牌、個人物品；正式版需遮蔽並訂定保存期限。
- 成本：大型模型只用在分析層；正式版以自訓小模型先篩，只把不確定的案例送大型模型（見文件 04）。
- 可追溯：每一筆 AI 判斷都保存模型名稱、輸入照片、輸出結果與理由，發生爭議時可以查證。
- 可替換：模型呼叫包成獨立模組，日後從 VLM 換成自訓模型時，不需改動其他部分。
