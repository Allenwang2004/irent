# 05 POC 實作步驟與評估方式

本文件說明 POC 的實作步驟、每一步的產出，以及如何評估成果。

本階段的交付物是計畫書與影片報告，因此 POC 以「網頁模擬」呈現：用行動網頁模擬 App 的拍照與上傳流程，用網頁看板模擬營運後台。

---

## 1. POC 範圍

| 項目 | POC 做法 |
|---|---|
| 使用者 App | 行動網頁模擬（拍照或選擇照片上傳、即時回饋、拍攝進度） |
| 即時品質檢查 | 真實運作：OpenCV 規則、預訓練 YOLO、車牌 OCR、小型 VLM |
| 車損比對與整潔度 | 真實運作：大型 VLM |
| 營運後台 | 網頁看板模擬（預警列表、照片比對、確認或駁回、工單） |
| 通知 | Slack webhook 或 LINE Messaging API 實際發送 |
| 車輛與訂單資料 | 以假資料模擬（SQLite） |

## 2. 實作步驟

| 步驟 | 內容 | 產出 | 依賴 |
|---|---|---|---|
| 1. 資料整理 | 整理主辦方照片，標註拍攝角度、有無車損、整潔度；切出測試集。資料未到之前，可先用自行拍攝或公開資料集（CarDD）的照片開發 | 測試資料集與標註表 | 主辦方資料 |
| 2. 品質檢查 API | 模糊與曝光規則、車輛框比例、車牌偵測與 OCR、小型 VLM 角度判斷 | `POST /check-quality` | 無 |
| 3. 使用者端網頁 | 拍照頁（輪廓引導框、逐張即時回饋、拍攝進度）、還車確認頁 | 可用手機操作的模擬頁面 | 步驟 2 |
| 4. 車損比對 API | 角度配對、影像對齊、大型 VLM 比對、結構化輸出 | `POST /compare` | 無 |
| 5. 整潔度 API | 評分準則加範例的大型 VLM 分類、遺留物清單 | `POST /tidy` | 無 |
| 6. 評估腳本 | 在測試集上批次執行，計算各項指標與延遲 | 評估報告 | 步驟 1、2、4、5 |
| 7. 預警與後台 | 事件分級規則、通知發送、營運看板、工單 | 營運後台網頁 | 步驟 4、5 |
| 8. 端到端串接 | 模擬一次完整的取車到還車流程，確認各環節串得起來 | 可重複執行的 Demo 流程 | 步驟 3、7 |
| 9. 調校 | 依評估結果調整 prompt 與閾值，整理成功與失敗案例 | 第二版評估報告、Demo 素材 | 步驟 6 |

步驟 2、4、5 彼此獨立，可以平行開發。

## 3. 建議專案結構

```
irent/
  plan/                 計畫書（本系列文件）
  note/                 原始筆記
  backend/
    app.py              FastAPI 進入點
    quality/            picture_quality：規則、偵測、車牌、角度
    compare/            車損比對：配對、對齊、VLM 判讀
    tidy/               整潔度分類
    alerts/             事件分級、通知、工單
    db/                 SQLite 資料表與假資料
  web/
    user/               使用者端模擬網頁
    ops/                營運後台看板
  eval/
    datasets/           測試照片與標註
    run_eval.py         評估腳本
    reports/            評估結果
```

## 4. 評估方式

### 4.1 測試資料

| 資料 | 用途 |
|---|---|
| 主辦方「進行索賠」照片 | 車損的正例 |
| 主辦方「沒有進行索賠」照片 | 車損的負例，用來量測誤報 |
| 主辦方車內照片 | 整潔度分類（需先人工標註三類） |
| 自行製作的劣質照片（模糊、太遠、無車牌、錯誤角度） | 品質檢查的測試 |

測試照片的數量要寫進報告，所有指標都要搭配樣本數呈現。

### 4.2 指標

| 功能 | 指標 | POC 參考目標（拿到資料後再校正） |
|---|---|---|
| 品質檢查 | 各問題類別的 precision、recall | recall 80% 以上 |
| 品質檢查 | p50、p95 延遲 | p95 在 2 秒以內（網頁模擬環境） |
| 車損比對 | recall | 盡量提高，漏報優先處理 |
| 車損比對 | 誤報率（負例中被判為有車損的比例） | 記錄即可，作為閾值調整依據 |
| 整潔度 | 混淆矩陣、整體準確率 | 「髒汙被判為乾淨」接近 0 |
| 分析層 | 每次還車從上傳完成到產生預警的時間 | 1 分鐘以內 |

### 4.3 閾值決定方式

1. 在測試集上取得每筆判斷的信心分數。
2. 畫出不同閾值下的 recall 與誤報率。
3. 以「recall 達標下誤報最少」為原則，決定「高信心直接預警」與「送人工確認」兩個閾值。

### 4.4 失敗案例分析

每一類錯誤至少挑出 2 至 3 個案例，記錄原因（例如反光被誤判為刮傷、角度差太大無法對齊），並提出改進方向。這些案例也會用在影片報告中（見文件 06）。

## 5. 風險與對策

| 風險 | 對策 |
|---|---|
| 主辦方資料量太少 | 以公開資料集與自行拍攝照片補充；報告中如實說明樣本數 |
| 取車照與還車照角度差異大，比對不準 | 影像對齊；使用者端輪廓引導框統一角度 |
| 光線、反光、雨水造成誤判 | prompt 明確要求忽略；失敗案例納入 few-shot 範例 |
| VLM API 延遲不穩定或逾時 | 設定逾時與重試；逾時進入人工佇列；錄影時準備備用錄製畫面 |
| 模型輸出格式不穩定 | 使用結構化輸出並做格式驗證，失敗時重試 |
