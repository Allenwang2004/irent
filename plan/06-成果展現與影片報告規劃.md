# 06 成果展現與影片報告規劃

本文件說明影片報告的結構、分鏡腳本、網頁模擬畫面需求，以及錄製注意事項。

本階段影片中的 App 與後台畫面，以網頁模擬呈現（見文件 05）。

繳交版本的影片限 3 分鐘，逐段腳本見文件 08；本文件第 2 節以 5 分鐘為例的時間分配僅供參考。

---

## 1. 影片報告目標

讓評審在短時間內理解三件事：

1. 問題是真的，而且很痛（營運人力與使用者體驗）。
2. 我們的方案可以運作（實際操作畫面，而不是只有投影片）。
3. 方案可以落地、可以持續演進（數據、延遲、自訓路線）。

## 2. 影片結構與時間分配

以下以 5 分鐘為例；若主辦方有時間限制，依比例調整。

| 段落 | 時間 | 內容 | 畫面形式 |
|---|---|---|---|
| 1. 開場與痛點 | 0:00 至 0:40 | 用情境開場：用戶取到髒車而客訴；營運人員每天人工看大量照片 | 投影片或情境示意圖 |
| 2. 解決方案總覽 | 0:40 至 1:10 | 三層架構：即時防呆、AI 分析、營運預警 | 架構圖（文件 02） |
| 3. Demo 一：即時防呆 | 1:10 至 2:00 | 拍攝模糊、沒拍到車牌的照片，立即出現重拍提示；重拍後通過 | 網頁模擬 App（手機畫面） |
| 4. Demo 二：新車損偵測 | 2:00 至 2:50 | 上傳一組取車與還車照片，後台出現預警，並排比對並標出車損位置與理由；同時收到通知 | 網頁模擬後台與通知畫面 |
| 5. Demo 三：整潔度與派工 | 2:50 至 3:30 | 上傳髒亂的車內照片，判為髒汙，自動建立清潔工單；另展示遺留物通知 | 網頁模擬後台 |
| 6. 成效數據 | 3:30 至 4:10 | 準確率（附樣本數）、延遲表、一個失敗案例與改進方式 | 表格與圖表 |
| 7. 演進路線與創新服務 | 4:10 至 4:45 | 從 VLM 到自訓小模型的三階段；取車前車況透明、責任時間軸、用戶獎勵 | 投影片 |
| 8. 結尾 | 4:45 至 5:00 | 一句話總結價值 | 投影片 |

## 3. Demo 分鏡腳本

### Demo 一：即時防呆

1. 手機畫面開啟模擬 App，進入還車拍照頁，畫面有車輛輪廓引導框，顯示「已完成 0 / 8 張」。
2. 故意拍一張模糊的左前方照片，約 1 秒內跳出「照片模糊，請保持手機穩定後再拍一次」。
3. 重拍一張距離太遠且沒拍到車牌的照片，跳出「沒有拍到車牌，請靠近一點」。
4. 正確重拍，顯示通過，進度變成「1 / 8」。
5. 畫面角落顯示這次檢查的耗時，強調「即時」。

### Demo 二：新車損偵測

1. 快轉完成剩下的拍照並按下還車。
2. 切換到營運後台，預警列表出現一筆「疑似新車損（高）」。
3. 點開事件：取車照與還車照並排，還車照上標出車損框，下方顯示 AI 判斷理由。
4. 切換到手機或電腦的 Slack 或 LINE 畫面，顯示剛收到的通知（車號、事件、縮圖、連結）。
5. 營運人員按下「確認」，車輛狀態變成「待維修」，下一筆預約暫停。

### Demo 三：整潔度與派工

1. 上傳一組髒亂的車內照片。
2. 後台出現「車內髒汙」預警，顯示分類結果與理由。
3. 自動產生清潔工單並指派給整備人員。
4. 另一組照片偵測到遺留物（例如手機），顯示客服通知。
5. 回到車況總覽，展示不同車輛的狀態顏色標示。

## 4. 網頁模擬需要的畫面

| 畫面 | 位置 | 必要元素 |
|---|---|---|
| 拍照頁 | 使用者端 | 輪廓引導框、應拍角度說明、拍攝進度、即時回饋訊息、檢查耗時 |
| 還車確認頁 | 使用者端 | 已拍照片縮圖、送出按鈕、「系統分析中，您可以離開」提示 |
| 取車前車況頁（創新服務） | 使用者端 | 上次清潔時間、整潔評分 |
| 車況總覽 | 營運後台 | 車輛列表、狀態顏色、區域篩選 |
| 預警列表 | 營運後台 | 嚴重度、事件類型、時間、狀態 |
| 事件詳情 | 營運後台 | 取還車照片並排、車損標示框、AI 理由、確認與駁回按鈕 |
| 工單 | 營運後台 | 工單類型、指派對象、狀態 |
| 通知 | Slack 或 LINE | 車號、事件、縮圖、後台連結 |

使用者端網頁建議用手機實際開啟並錄影，或用瀏覽器的手機模擬模式錄製，讓畫面看起來像 App。

## 5. 讓評審信服的做法

- 所有準確率都附上樣本數，例如「在 N 組主辦方照片上，車損 recall 為 X%」。
- 列出延遲表（p50、p95），直接回應題目的「即時」要求。
- 主動展示一個失敗案例並說明改進方向，比只展示成功案例更可信。
- 營運效益估算要寫清楚假設，例如「假設每日還車 N 筆、每筆人工檢視 M 秒，可節省 X 小時」。
- Demo 使用真實運作的 API，不是寫死的畫面；可在影片中短暫露出 API 回傳的 JSON 佐證。

## 6. 錄製注意事項

1. 先寫好逐字稿，每一段對應分鏡，控制總長度。
2. Demo 分段錄製再剪接，避免一次錄到底時 API 延遲或出錯。
3. 每段 Demo 保留一份完整成功的錄影作為備份素材。
4. 錄製前準備好測試照片（模糊、無車牌、有車損、髒亂、有遺留物各一組），並確認每組結果穩定。
5. API 等待時間較長的片段可以加速播放，但要在畫面上標註「已加速」，並另外誠實呈現實際延遲數據。
6. 畫面解析度至少 1080p；手機畫面與後台畫面可以用分割畫面同時呈現因果關係（使用者上傳，後台立即出現預警）。
7. 字幕與旁白使用一致的名詞：即時防呆、新車損偵測、整潔度分類、營運預警。
