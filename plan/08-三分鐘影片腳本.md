# 08 三分鐘影片腳本

本文件是繳交用 3 分鐘影片說明的腳本，包含時間軸、畫面、旁白與字幕。App 與營運後台畫面以網頁模擬呈現。

文件 06 的影片規劃以 5 分鐘為例；本腳本是依繳交要求壓縮成 3 分鐘的版本，以本文件為準。

---

## 1. 腳本原則

- 中文旁白語速約每秒 4 字，3 分鐘旁白控制在 700 字左右，保留畫面停頓與轉場的時間。
- 前 20 秒就要讓評審知道問題與解法，Demo 佔一半以上時間。
- 畫面與旁白要同步：旁白講到哪個功能，畫面就出現那個功能的操作。
- 數據尚未取得的地方以 `[待補]` 標示，錄製前替換。

## 3. 逐段腳本

### 段落 1：痛點（0:00 至 0:20）

| 項目 | 內容 |
|---|---|
| 畫面 | 情境示意：一邊是後台人員面對滿螢幕的車況照片；另一邊是用戶打開車門看到車內髒亂 |
| 字幕標題 | 照片很多，人力不夠，問題發現得太晚 |

旁白：

> iRent 用戶每次取車、還車都要拍照留存車況。但後台需要大量人力逐張查看，車損和髒亂很難第一時間攔截；用戶也常因為照片拍錯而不自知，或是承接到上一手的髒車。

### 段落 2：方案總覽（0:20 至 0:40）

| 項目 | 內容 |
|---|---|
| 畫面 | 三層架構圖，依旁白逐層亮起 |
| 字幕標題 | iRent 智能車況管家 |

旁白：

> 我們的智能車況管家分成三層：上傳當下，即時防呆，一秒內告訴用戶要不要重拍；還車後，由 AI 比對車損、判斷整潔度；一旦發現異常，立即通知營運人員並自動派工。

### 段落 3：Demo 一 即時防呆（0:40 至 1:15）

| 時間 | 畫面 | 字幕 |
|---|---|---|
| 0:40 | 手機畫面開啟模擬 App 還車拍照頁，顯示輪廓引導框與「已完成 0 / 8 張」 | 環節一：即時防呆 |
| 0:48 | 拍一張模糊照片，約 1 秒後跳出「照片模糊，請保持手機穩定後再拍一次」 | 模糊偵測 |
| 0:56 | 拍一張距離太遠、沒拍到車牌的照片，跳出「沒有拍到車牌，請靠近一點」 | 車牌與距離檢查 |
| 1:05 | 正確重拍，顯示通過，進度變成「1 / 8」，角落顯示檢查耗時 | 檢查耗時 [待補] 秒 |

旁白：

> 用戶拍照時，畫面上有輪廓引導框。如果照片模糊，系統馬上提醒重拍；距離太遠、沒拍到車牌，也會具體告訴用戶該怎麼調整。重拍之後立即通過，整個檢查在一秒左右完成，照片一次拍對，後續的判讀才可靠。

### 段落 4：Demo 二 新車損偵測（1:15 至 1:55）

| 時間 | 畫面 | 字幕 |
|---|---|---|
| 1:15 | 快轉完成拍照並按下還車，顯示「系統分析中，您可以離開」 | 還車完成 |
| 1:20 | 切換到營運後台，預警列表出現「疑似新車損（高）」 | 環節二：新車損偵測 |
| 1:27 | 點開事件：取車照與還車照並排，還車照標出車損框，下方顯示 AI 判斷理由 | 取車照 vs 還車照 |
| 1:40 | 分割畫面：Slack 或 LINE 收到通知（車號、事件、縮圖、連結） | 即時通知 |
| 1:48 | 營運人員按下「確認」，車輛狀態變成「待維修」，下一筆預約暫停 | 人工確認，暫停出租 |

旁白：

> 用戶還車後不需要等待，AI 在背景比對同一角度的取車照和還車照，只找出這次租車新增的車損。後台立刻出現預警，標出車損位置並說明判斷理由，營運人員同時收到通知。確認之後，車輛自動暫停出租、等待維修；不確定的案例則交給人工判斷。

### 段落 5：Demo 三 整潔度與派工（1:55 至 2:25）

| 時間 | 畫面 | 字幕 |
|---|---|---|
| 1:55 | 上傳髒亂的車內照片，後台出現「車內髒汙」預警與判斷理由 | 環節二：整潔度分類 |
| 2:05 | 自動產生清潔工單並指派給整備人員 | 環節三：自動派工 |
| 2:13 | 另一組照片偵測到遺留手機，顯示客服通知 | 遺留物通知 |
| 2:20 | 回到車況總覽，各車輛以顏色標示狀態 | 車況一目了然 |

旁白：

> 車內照片會被分成髒汙、普通、乾淨三類。判定髒汙時，系統自動開立清潔工單給整備人員，這台車清潔完成前不會出租給下一位用戶。系統也能發現遺留物品，主動聯繫上一位用戶。

### 段落 6：成效與演進（2:25 至 2:48）

| 時間 | 畫面 | 字幕 |
|---|---|---|
| 2:25 | 成效數據表（recall、誤報率、延遲，附樣本數） | 在主辦方資料上的實測結果 |
| 2:37 | 三階段演進時間軸：VLM 先行、蒸餾與標註、自訓小模型 | 技術演進路線 |

旁白：

> 在主辦方提供的 [待補] 組照片上，車損偵測 recall 達到 [待補]，品質檢查平均 [待補] 秒完成。現階段先用大型模型快速上線，並累積人工確認的資料，未來訓練專用小模型放進手機，讓速度更快、成本更低。

### 段落 7：結尾（2:48 至 3:00）

| 項目 | 內容 |
|---|---|
| 畫面 | 標語與隊名 |
| 字幕標題 | 讓每一次取車都安心，讓每一張照片都有用 |

旁白：

> iRent 智能車況管家，讓每一次取車都安心，讓每一張照片都有用。謝謝。

## 5. 錄製前準備清單

| 項目 | 說明 |
|---|---|
| 測試照片 | 模糊、太遠無車牌、正確、有新車損（取還車各一）、車內髒亂、有遺留物，各一組 |
| 模擬資料 | 車輛、訂單、既有車損紀錄的假資料，確保每次 Demo 結果一致 |
| 通知帳號 | Slack 或 LINE 測試頻道 |
| 畫面錄製 | 手機畫面（實機或瀏覽器手機模擬模式）與後台畫面分開錄，後製時合成分割畫面 |
| 旁白錄音 | 依本腳本逐段錄製，對齊時間軸 |
| 數據替換 | 錄製前把所有 `[待補]` 換成評估報告的實際數字 |

## 6. 錄製與後製注意事項

1. 各段分開錄製再剪接，避免 API 延遲影響節奏。
2. 分析層等待時間可以加速播放，但畫面上要標示「已加速」；即時防呆的片段不要加速，才能呈現真實延遲。
3. 字幕和旁白使用一致名詞：即時防呆、新車損偵測、整潔度分類、營運預警。
4. 輸出解析度至少 1080p，總長度控制在 3 分鐘以內。
